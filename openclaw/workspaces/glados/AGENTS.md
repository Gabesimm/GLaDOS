# GLaDOS team

This team can read, write, edit files, and run commands directly. For almost every request, just do the work yourself (or delegate it, see below) — do not draft a plan or ask permission first, and do not wait for a confirmation that isn't needed.

The one exception is a destructive step: deleting an existing file or folder, uninstalling software, overwriting or replacing content that already exists, formatting/wiping something, or any other action that destroys something rather than adding to it. Before doing that specific step, state in one sentence exactly what will be deleted or overwritten, ask "Shall I proceed?", and end that reply with [[CONFIRM]]. Only carry out that destructive step after the user confirms. Everything else — creating new files, non-destructive edits (adding/appending/modifying in place without erasing prior content you weren't told to remove), running commands, installing or uninstalling nothing yet decided, reading, building, searching — runs immediately without asking.

This includes editing openclaw.json itself and enabling/configuring plugins: use `openclaw config patch` (never hand-edit the JSON file directly) via `exec`, then verify with `openclaw plugins list` or `openclaw config get`. There is no separate "owner-only" configuration authority you are missing — full read/write/exec already covers this. If a command reports a real blocker (e.g. "blocked by allowlist"), fix the actual blocker yourself (e.g. add the plugin id to `plugins.allow` in the same patch) instead of concluding you lack permission to edit configuration at all.

A pending destructive-step confirmation only stays available for as long as your replies keep asking for it. If it's awaiting the user's decision and their next message is not a clear yes or no (e.g. "has it finished?", a clarifying question, small talk), answer it and then end that same reply by restating the exact destructive step verbatim, followed by "Shall I proceed?" and [[CONFIRM]] again, so the offer stays live. Only drop it if the user explicitly cancels or changes the request.
Never let [[CONFIRM]] attach to a reply that is itself only about the confirmation mechanism (e.g. "the plan is still pending", "that didn't reach the server", "is it still in effect") — that text is not the destructive step, and if it gets confirmed it would be carried out as if it were the task, which breaks everything. Only ever end with [[CONFIRM]] directly beneath the real, exact destructive step itself.

## Preferred desktop/browser interaction: independent of OpenClaw's computer tool
These two local helpers exist and are the default for any real mouse/keyboard interaction (clicking, typing, scrolling) and for finding what to click — reach for them before the `computer` tool, not as a fallback after it. Both run via `exec`, use raw Windows APIs directly, and never touch OpenClaw's gateway/node dispatch path — they are completely immune to the `COMPUTER_HOST_BUSY` / "Gateway client authority closed" lock (see below), and they work in apps the `browser` tool doesn't support (e.g. Opera GX).
- `Find-UIElement.ps1 -ProcessName <name> -Action List [-Filter <text>] [-TitleContains <text>]` — lists real, named, clickable elements (buttons, links, tabs, page content) with their exact click coordinates, using Windows' own UI Automation tree. Confirmed working against real Chromium page content in Opera GX (found real page links/buttons, not just browser chrome), not just native app UI. Use this instead of guessing coordinates from a screenshot.
- `Find-UIElement.ps1 -ProcessName <name> -Action Click -Name <text>` — finds an element by Name (contains match, case-insensitive) and clicks it: tries the UIA Invoke pattern first, falls back to a real mouse click at its center when Invoke isn't supported. Prefer this over raw coordinate clicking whenever the target has a discoverable name.
- `Find-UIElement.ps1 -ProcessName <name> -Action GetText -Name <text>` — reads an element's value/name without clicking it.
- `Send-Input.ps1 -Action MouseMove|MouseClick|MouseScroll|KeyType|KeyCombo ...` — direct mouse/keyboard control for anything `Find-UIElement.ps1` can't target by name (freeform clicking at known coordinates, typing into whatever currently has focus, key combos like `CTRL+A` or `ENTER`). `Find-UIElement.ps1 -Action Click` already calls into this automatically as its fallback, so you rarely need to compute coordinates yourself.
Different UI frameworks report control types inconsistently (WinUI3 apps like modern Notepad expose real buttons as generic "Pane", not "Button"), so `List`/`Click`/`GetText` match on having a Name at all rather than filtering by control type — read the `Name` column to find what you want, not `ControlType`.
`List` returning nothing is a real, known limitation, not just a sign to give up: some pages (canvas/WebGL-rendered configurators, heavily custom-styled interactive builders — a pizza-builder page is a plausible example) don't expose a populated accessibility tree at all. When that happens: (1) retry `List` once after a couple of seconds — some pages build their accessibility tree lazily; (2) try `-TitleContains` to make sure you're actually targeting the right window/tab, since a wrong target also returns nothing; (3) only if both genuinely find nothing, fall back to the `computer` tool with a screenshot to visually ground a coordinate click — say plainly that you're doing this because the page has no exposed accessibility tree, don't just silently fail or claim the task is impossible.
Reserve `computer`/`screen.snapshot` for genuinely visual verification (confirming rendered appearance, reading arbitrary pixels), the screenshot step itself, or the no-accessibility-tree fallback above; `Capture-Monitor.ps1` (see below) remains the way to actually capture a specific monitor, on any target.

## Viewing a screenshot you took
`computer`/`screen.snapshot` returns the captured image as base64 image data inside the tool result, not as something you can see directly — that data is text to you until it's on disk. The `view_image` tool only accepts a local file path or URL, never inline base64. To actually see a screenshot: decode the returned base64 and write it to a temp PNG (e.g. a short `exec` call that saves it under a scratch folder), then call `view_image` with that file's path. Skipping the save step and just reading the base64 text is not "viewing" it — say so plainly rather than describing the raw text as an image you looked at.

## Windows desktop limits and integrity
The `computer` tool's `cua-computer` driver only ever captures the primary display — this is a hardcoded restriction in the driver itself (`displayId: "primary"`, and any other screen index is explicitly rejected), not a config setting, so don't retry it with a different screenIndex or claim it might work with node vs. gateway targeting.
For a screenshot of a **non-primary monitor**, don't use the `computer` tool at all — use `exec` to run the local `Capture-Monitor.ps1` helper instead, which captures any monitor directly via Windows' own screen APIs, completely independent of the driver: `Capture-Monitor.ps1` (no args) lists all monitors with their index/bounds/primary flag; `Capture-Monitor.ps1 -Index N` captures that monitor to a temp PNG and reports the saved path. Then `view_image` that path to see it, or attach it to a reply the same way as any other saved screenshot. This has been tested and works for real secondary-monitor content.
On an integrity-level input refusal, take a fresh observation and check the actual target/window; do not infer that Discord is elevated or elevate the whole node. If the target app itself is elevated, ask the user to relaunch that app normally when practical. Never repeatedly send keystrokes after Windows reports them blocked.
For a request to open or foreground an application when no explicit window-focus operation is available, use that application's ordinary per-user launch path or a clearly identified taskbar click, then verify its window. Do not send keystrokes to an elevated foreground window; stop on an integrity refusal and explain the specific blocker.
To **launch an app and bring it to the foreground in one step** (e.g. "open Discord and screenshot it"), use `exec` to run the local `Open-App.ps1 -Path <exe> -ProcessName <name>` helper instead of `Start-Process` directly, then verify its `Focused` result before taking a screenshot. Two things it exists specifically to work around, both confirmed on this machine:
- **The launched process is not the real app.** Many Windows apps use a launcher/updater stub that exits almost immediately after handing off to a differently-PID'd real process (Discord's Squirrel `Update.exe`/`Discord.exe` pattern), or a single-instance app (browsers like Opera GX) whose second invocation just signals the already-running instance and exits. Tracking the PID `Start-Process` returns, or checking once immediately after launch, reads either of these as "exits immediately, no window appears." `Open-App.ps1` polls by process name for a real visible window (skipping known transient titles like "...Updater") instead of trusting the original PID.
- **A background process cannot silently steal foreground focus.** Plain `SetForegroundWindow` from a non-interactive-foreground process (this one) is blocked by Windows' foreground-lock restriction: the call reports success, the window even restores, but focus stays wherever it was — this reads as "activated the window but it didn't come to the foreground." `Open-App.ps1` (and `Focus-Window.ps1`, for an already-running app) works around this correctly, by attaching input to whichever thread currently owns the foreground window (not the target's own thread — that alone is not sufficient) plus a harmless Alt-key tap, before calling `SetForegroundWindow`. Do not attempt a simpler version of this yourself; both tricks are required together.
For a precise open/foreground request when the app is **already running**, use the local `Focus-Window.ps1` helper with the target process name (and optional title fragment), then verify its `Focused` result. If the app is not running yet, use `Open-App.ps1` instead so the launch and the foreground-activation race is handled correctly. Never interpret a screenshot alone as proof that a window received focus — check `Focused` first.
Both helpers also report `MonitorIndex` / `MonitorIsPrimary` for the window they just focused (computed from its actual on-screen position, not a guess). **Use that value directly** — if `MonitorIsPrimary` is `False`, the `computer` tool's primary-only screenshot will never show this window no matter how many times you retake it or how genuinely focused the app is; go straight to `Capture-Monitor.ps1 -Index <MonitorIndex>` instead. Do not conclude a launch failed, that the focus check is "a false positive," or alternate blindly between monitor screenshots when `Focused: True` but the app isn't in the picture you happened to check — check `MonitorIndex` first, it tells you definitively which capture will actually show it.
For a request that wants **proof the app is visible** ("open X and screenshot it"), add `-Capture` to either helper (`Open-App.ps1 ... -Capture` or `Focus-Window.ps1 ... -Capture`) instead of running a separate `Capture-Monitor.ps1` call afterward. This captures the correct monitor immediately, inside the same script run, right after confirming focus — no second `exec` round trip, no gap. Splitting focus and capture into two separate `exec` calls leaves a real window (seconds, sometimes less) where a transient window can close, another app can regain focus, or a page can renavigate before the second call runs, so a screenshot from that second call can show something else entirely even though the first call's `Focused: True` was completely accurate at the time. `-Capture` returns `ScreenshotPath` directly in the same result object — `view_image` that path.

## Desktop control lock handling
All desktop and browser UI actions issued through the `computer` tool share one physical screen and must be serial: send one action, wait for its result, then observe before acting again. Never parallelize `computer` calls or send them from a helper agent. Prefer the paired PC node as specified above. If the Gateway target returns `COMPUTER_HOST_BUSY`, stop using that route and use the paired node; the Gateway can retain its lease for up to five minutes after its last completed action. If the node itself returns busy, stop input and allow the current action to finish or its owner to close, then take a fresh screenshot before resuming. Do not ask the user to restart the Gateway for a Gateway-only lock — that's a known upstream OpenClaw bug (traced to `server-plugin-in-process-dispatch-DeqbsaqC.mjs` and `computer-service-Bz9CorXX.mjs` in this install), already reported, with no config fix available. For any task involving several successive clicks/keystrokes (exactly what triggers this lock), use `Send-Input.ps1`/`Find-UIElement.ps1` instead of `computer` from the start — they never touch this code path at all, so the lock cannot occur.
